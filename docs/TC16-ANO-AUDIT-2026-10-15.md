# TC16 and Ano follow-up — 2026-10-15

The Python TC16 implementation and the preserved native ETP VM deliberately have
separate byte encodings, as already declared in `ECOSYSTEM.md`. Source comparison
confirmed concrete differences; no bytecode migration or implicit translation
was added.

| Contract | Python `ziokt.tc16` | Native ETP `tc16_tcc.rs` |
|---|---|---|
| Opcode 0x01 | MOV, followed by register pair | NOP |
| Stack | Separate `sp`, initial memory length | R15, initial 0xFEFE |
| Frame/link registers | Compiler's own calling convention | R14/R13 |
| Flag 0x40 | Half carry | Execution fault |
| Host interaction | Explicit supplied syscall capabilities | Native storage/SystemBus/MMIO |

The same 16-bit register width does not establish ABI compatibility. Native
opcode semantics, interrupt behavior, and compiler output were reviewed only;
no Rust compile, execution, or Python-to-native bytecode test was performed.

Ano's existing formal specification distinguishes `ano.boolean.v1` from
`ano.refined-equality.v0`. The v1 unknown state is absorbing, while the v0 equality
model treats it as an ordinary third comparable value. The Python module header
now makes its binary compatibility claim precise instead of implying identical
third-state behavior.

One actual input-validation defect was fixed: `defence` built a set of required
claim names before checking that names were strings. A list/dict claim raised a
raw TypeError. Names are now checked first, and malformed claims consistently
raise ProtocolError. A regression test covers unhashable, numeric, and duplicate
claim names. Authorization still requires all required verified claims and never
claims cryptographic assurance from algebraic identities.

Executed in the repository with Python 3:

```
python3 -m unittest discover -s tests -p test_ano_laws.py -v
python3 -m unittest discover -s tests -p test_tc16.py -v
```

Results: Ano 3 passed; TC16 5 passed. These are the existing focused implementation
and finite-law tests plus the new malformed-claim regression. They do not prove
unbounded arithmetic closure, native/Python ABI equivalence, application-level
authorization evidence provenance, full original tool interoperability, or
all requested adversarial/lifecycle scenarios.

## Complete numeric operations through the common application entry

The ZDA route now exposes `ano.calculate` over the existing exact operations:
ZDA add/sub/mul/div, AnoNumber add/mul and AnoVector add/dot. Inputs use
`ziokt.zda-number.v1`, `ziokt.ano-number.v1` or `ziokt.ano-vector.v1` documents.
Fractions carry canonical reduced numerator/positive denominator strings, are
bounded to 4096 bits and reject floats, zero denominators and alternate encodings.
Ano documents explicitly select `ano.boolean.v1`. This additive format does not
change the existing ZDA document or legacy truth profiles.

`ano.defence` exposes the existing ALLOW/DENY/HOLD logic with bounded caller
claims and explicitly labels its result as no cryptographic proof. Unknown
claims cannot become authorization. Both operations remain owner-granted methods
on the `zda` route; they do not grant host file/network access.

TCC now rejects truncated source with `INVALID_TCC` rather than leaking an
IndexError, and bounds significant integer digits before conversion. Long runs
of leading zeros remain valid. Six TC-16/TCC regressions passed (0.019 seconds),
including existing VM/stack/interrupt/recursion/short-circuit cases.
