# Worker签名回执与发布验证

本机制为已批准Worker的结果提供可验证归属、输入/输出绑定和重放防护，不是无信任计算证明，不产生Corium奖励、质押权重或区块提议资格。Worker身份、不同签名密钥、不同故障域、真实重建、原生治理和实际结算必须分别验证。

## 真实执行路径

1. 操作者先批准Worker资源与项目，再通过管理员专用 `/v1/workers/signing-key`（CLI `worker-signing-key FILE`）绑定Ed25519公钥及核查证据SHA-256。Worker不能自行批准密钥。正在运行任务时拒绝变更密钥。
2. Runner使用本地0600密钥文件 `runner --signing-key-file KEY`，在真实OCI执行并将产物/日志写入原生对象存储后签署结果。密钥不进入容器、API请求、发布包或浏览器。只有公钥、签名与哈希进入来源记录。
3. 回执域 `OpenCI/worker-receipt/v1`，载荷绑定精确pipeline、task、attempt、Worker、source对象/摘要、完整任务规范摘要、租约摘要和结果对象。没有原始租约令牌、源码正文、日志正文或密钥。
4. Controller使用独立批准公钥校验精确载荷后，在完成任务的同一SQLite事务中持久化签名。签名缺失、错域、错密钥、跨任务/重试/输入/产物替换全部拒绝。重试必须与已有结果和签名一致。
5. 独立验证拒绝两个Worker名字共用同一签名密钥。发布准备及最终落库重新验签与复查当前授权；密钥轮换使旧签名不能授权新发布。旧签名保留供审计，不能强行转换为新密钥签名。
6. 原生dCPM签名包中的provenance.json保存两侧签名回执，安装后仍可独立验证，原生签名/安装/回滚路径保持不变。

## 兼容、持久化与边界

数据库新增`worker_receipt_keys`和`receipt_attestations`，不删除旧表、历史任务或结果。没有注册签名密钥的旧Worker仍能完成普通CI，但不形成签名贡献凭证。对已要求签名的Worker，旧未签名任务不能用于新发布，需真实重建。旧发布结果的幂等重试不改变历史。

当前签名不是硬件远程证明，两个公钥不证明两个物理主机，也不能排除串谋。operator故障域证据和不同物理主机需要独立核查。CI双次OCI执行仍在同一CI主机，记录`distinct_hosts:false`。确定且有界的原生贡献准入、链上去重、治理批准、结算与回滚尚未完成，`corium_settled:false`保持不变，主网规则未修改。
